# Architecture and permission boundary

## Current stack

- Runtime: Node.js 20+ with native ECMAScript modules (JavaScript), npm scripts, built-in test runner. No dependency installation or TypeScript migration in this stage.
- Interface: terminal chat, a local HTTP model configuration page, and the localhost-only Local Gateway (`npm run gateway`).
- Model protocol: OpenAI-compatible Chat Completions with a Provider registry for OpenAI-compatible endpoints and Ollama/no-key local endpoints.
- State: `.agent-data/models.json` stores provider metadata and Secret references; encrypted Secret material is stored separately in `.agent-data/secrets.json`. Sessions and service state are excluded from version control.

The earlier working JavaScript implementation remains in place. A TypeScript/pnpm migration is a separate decision; do not mix it with permission changes.

Flow: command input is handled before the model -> high-confidence workspace intent rules select the visible tool surface and `tool_choice` mode -> model returns text or a tool call -> dispatcher checks the full registry -> validates arguments and path -> policy/approval/hooks -> workspace operation -> structured tool result to model. A model-supplied tool name never grants a capability by itself.

Each Gateway turn also owns a bounded, durable tool timeline and, for project/development requests, a structured plan. Plans validate phase/step dependencies and executable acceptance criteria before any operation; generation or validation failure fails closed. Supported checks include tool success, tool-result text, workspace file existence/content, command exit status and phase all-steps completion. Plan updates are persisted before execution continues. Runtime dispatch gates tools against ready plan steps and continues to use the ordinary policy/approval layer. Phase dependencies unlock only after explicit phase acceptance passes. The Workbench shows phases, acceptance status/reasons, step attempts and recoverable actions. An interrupted structured turn can recover through `/api/turns/:id/recover`; the original request is fingerprint-checked, completed steps remain complete, and an in-flight side-effect step becomes `uncertain` rather than being replayed. `POST /api/turns/:id/retry-step` retries one eligible failed step within its declared tool surface; uncertain side effects require explicit user confirmation. Eligible acceptance failures can trigger at most two replans, preserving and validating completed steps and stopping on uncertain effects. Ordinary whole-turn retry remains a separate new turn and does not inherit tool permissions from the previous plan.

Workbench project workspaces are selected through a host-side Windows folder picker and stored in a bounded recent-project registry. Project identity/path is snapshotted into a newly created session; existing sessions without project metadata remain ordinary sessions. Every turn resolves its workspace, file tools, and command sandbox from the saved session project, and rejects a missing project directory rather than falling back to the gateway root. Explicit absolute paths continue through the existing external-file policy and approval flow. Project selection alone does not enable personal mode or bypass write approvals.

Interactive ambiguity uses the separate `ask_user` read-only tool. It is visible only in the interactive Gateway turn surface, accepts a bounded question and 2-8 unique option IDs, and pauses the turn as `awaiting_clarification`. The Gateway validates client identity, turn state and option membership before resuming the same turn. The selected label is untrusted user data and is passed as continuation context; it cannot change the tool allowlist, security mode or approval policy. CLI/background/inbound runners do not expose this interaction tool.

Tools are grouped into `workspace.read`, `workspace.write`, `external.read`, `external.write`, `sandbox.command`, `process.control`, `message.send`, and `task.control`. The turn's visible set is frozen and enforced again at execution, including for model-supplied calls to a hidden tool. Side-effect tools are never query-cached and require readiness plus their own approval. The CLI requires verified isolation and writable audit storage: failures disable every tool, never silently reverting to host reads. The Local Gateway is localhost-only by default and can require a Bearer token when configured.

## Policy today

- `file_info`, `read_file`, `list_files`, `find_files`, `search_text`: available to the main agent. Metadata reports file type, size, modification time and a text line count for UTF-8 files under 2 MB. Ranged reads support up to 200 lines from a 2 MB UTF-8 file; ordinary whole-file reads retain their 40,000-character limit. Listing defaults to `{items, nextCursor}` with 100 entries per page; filename and literal text searches return continuation cursors, scanning at most 2,000 entries per page (text search skips files over 100 KB). Cursors are process-local and expire after 10 minutes. `.agent-data`, `.git`, `.env*` and `node_modules` are excluded from listing/search. For complete-enumeration intents, the agent prompts the model to continue; if a cursor remains at final answer, the answer is marked partial.
- `write_file` and `edit_file`: the model can request them. A change is prepared and previewed before an explicit terminal `y` approval. `edit_file` requires one unique exact old-text match. Single-use workspace-bound preview tickets expire after five minutes. Callbacks receive copies, not mutable commit payloads. Hard-linked targets are rejected. The commit checks the target's identity, metadata and content hash again; new files use exclusive creation. Concurrent mutation after that final check is not prevented by an OS sandbox or transaction. Enter or any other answer denies the write.
- `external_write_file` and `external_edit_file`: the model can request one absolute external regular file at a time. The parent directory and target are checked for private names, links, hard links and Alternate Data Streams; the full path and diff require a fresh approval. Approval is followed by parent/target identity revalidation before the existing trusted commit broker publishes the change. This remains an application-level boundary: a hostile process can still race the final leaf replacement, and no directory-level or recursive write permission is granted.
- Access grants remain as a backend compatibility layer for existing configurations and API clients, but are no longer exposed as a Workbench feature. Safe mode uses per-operation external-read and file-write approvals; personal file mode permits ordinary file reads and single-file create/edit operations without a grant, while still rejecting protected paths, links, hard links and writes detected inside another project root. All modes keep audit and target revalidation.
- Security mode: `safe` preserves the fail-closed sandbox and approval boundary. `personal` is an explicit high-freedom file mode, not unrestricted host execution: ordinary file tools run through the host file boundary without the read snapshot/approval gate, while command, delete, network, message, task, MCP and plugin tools retain their own readiness and approval requirements. The mode is stored in `.agent-data/security-mode.json` and can be changed through `/api/security-mode` or the CLI.
- Tool surface: the filesystem group can be filtered by category and explicit allowlist, including wildcard prefixes. High-confidence workspace list/search/read/edit/write intents expose the filesystem group; general questions retain automatic tool choice.
- Result validation: read/list/search tools validate their host-side return shape before sending success to the model. Invalid results become structured `INVALID_TOOL_RESULT` errors.
- `sandbox_command` is visible only after the WSL2 + Bubblewrap isolation probe passes and requires per-call confirmation. Its workspace mount is read-only and network namespace isolated; output and duration are bounded. Linux supervisor limits address space, CPU time, file size, descriptors, core dumps and per-real-UID process counts. These are not aggregate cgroup quotas. EOF on the host cancellation pipe stops the process group; namespace teardown destroys descendants. Trusted Python reader and supervisor are mounted read-only from the project, so project source integrity is part of the trust model. Other host command tools, web access and sub-agents remain unavailable.
- Security audit records dispatch start/end with correlation IDs, outcomes and duration, never payloads. CLI audit failure prevents further operations. An end-record failure can occur after a write committed; the result explicitly warns about uncertain effects. This is not a tamper-proof event store.
- The conversation loop returns structured tool observations to the model for further decisions. High-confidence workspace fact intents use `tool_choice: required` for up to two enforcement attempts if the model answers without evidence; after a successful read/list/search result, the loop returns to `auto`. Defaults are 24 model rounds, 64 tool calls and 5 consecutive tool errors, bounded by hard maxima of 64, 256 and 8 respectively.
- The full linear transcript remains in `session.messages`. `session.context` stores a summary and a start-index checkpoint; model requests project only that checkpoint plus recent full turns. `/reset` advances the checkpoint without deleting raw history. Context estimates include serialized messages and tool definitions, reserve output and safety margin, and fail closed if the active request still does not fit. This is not a tokenizer-accurate guarantee.
- Model API requests: network access is made by the trusted application to the selected configured endpoint. File contents shared in chat/tool results may be sent to that endpoint. Choosing an endpoint is a trust decision.
- Query engine: OpenAI-compatible JSON and SSE Chat Completions, bounded retries before a successful HTTP response for network/429/5xx failures, 60-second total timeout and per-connection streaming opt-out. An interrupted stream is not retried; partial assistant text is never committed to the session.
- UI configuration operations: local loopback only, exact Host/Origin checks on writes. API Keys are stored through Windows DPAPI (or an explicitly configured encrypted fallback) and only a `secret://` reference is persisted in model metadata. Secret values are not returned by listing APIs and are excluded from session, cache, usage, audit and event payloads.

## Isolation limits

The main Agent process still has the current user's OS permissions; a bug, malicious dependency, concurrent filesystem mutation, or another route in future code could bypass application-level guards. With the verified WSL2 backend, `sandbox_command` and read-only file operations run in separate read-only/offline child processes. File writes and model requests remain in the host. Symlink checks, external target identity revalidation, and read-only mounts do not provide an atomic Windows approval-to-open transaction or a complete security boundary against concurrent path substitution and Windows junction/reparse-point behavior. Do not add arbitrary Python, writable command execution, or unrestricted web fetches on the host-process file-tool foundation.

Before adding new tools, decide resource scopes (path/host/command), default-deny behavior, one-time versus per-action approval, output limits and timeouts, audit requirements, and whether a platform-level sandbox is available. Add denial and escape tests for every new capability.
